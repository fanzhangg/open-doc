## 协作编辑体验改进

### 概述

本方案理顺人和智能体在 OpenDoc 里协作的方式。核心原则只有一条：**智能体是
一个普通的协作者**：用回复说明自己做了什么，评论串由人来解决。

在此基础上，参考 Google Docs 的协作体验（只是参考，不是复刻）改进两件事：
智能体修改文档的过程看得见；人和智能体同时编辑时互不打断，谁的文字都不丢。

方案不改变数据模型的基础：磁盘上的 markdown 仍是唯一的真实来源，评论仍在
sidecar 里，锚定、保存时保留未改动块的原始字节都保持不变。sidecar 格式只
增加字段（修改方案、应用通知），旧文件仍然有效。

相关文档：[产品设计](product-design.md)、[桌面应用设计](desktop-app.md)、
[格式规范](../spec/SPEC.md)、[智能体技能](../skills/opendoc/SKILL.md)

### 问题

- **智能体什么时候会回应，说不清。** 默认设置下，没有 @ 任何人的评论也会
  唤醒智能体（SPEC §5 的“或者没有提及任何人”，`mentionsOnly` 默认为
  `false`）。人给自己记的备注也会触发一次运行。
- **智能体会自己解决评论串。** 它认为改完了就 resolve，编辑器随即隐藏这个
  评论串。人可能没看到它改了什么，也没有机会说“不对”。
- **只有一种权限：直接改。** 想先看方案再决定时，只能在评论里写“先别改”。
- **修改像“神迹”。** `applyMarkdown`（`web/editor.js`）用 `replaceWith` 一次
  替换所有变化的块。改动跨几个段落时，很难看清改了什么、从哪里改起。
- **同段落冲突会打断人。** `merge3`（`web/merge.js`）按行（约等于段落）合并，
  双方改了同一段就弹出“Needs your choice”，要求在两个完整版本之间二选一。
- **修改记录不准。** 运行结束时，调度器比较“认领时”和“结束时”的整篇文档，
  把差异都记成智能体的修改（`dispatcher.js` 的 `#recordEdits`）。人在运行
  期间的输入也会被记进去，评论卡片上的“Undo”可能撤销人自己的文字。
- **双方看不见对方。** 运行开始后的十几秒到几十秒里页面没有任何动静；智能体
  也不知道人正在写哪一段，会径直改那一段。

### 原则：智能体是普通协作者

| | 真人审阅者（如 `@alex`） | 智能体（如 `@claude`） |
| --- | --- | --- |
| 什么时候回应 | 被 @ 时 | 人的评论和回复，只 @ 了别人的除外 |
| 怎么修改文档 | 自己动手改 | 按权限：直接改，或提出修改方案等人批准 |
| 处理完之后 | 在评论串里回复 | 在评论串里回复，说明改了什么 |
| 谁来解决评论串 | 人 | 人；智能体不能解决 |

1. **不需要 @。** 评论串里最新一条人的消息 @ 了智能体，或者没有 @ 任何人，
   它就处理；只 @ 了别人的评论留给那个人。追问不需要再 @。撤销和应用方案的
   通知不会唤醒它。（最初的方案要求必须 @，试用后觉得增加了麻烦，已取消。）
2. **两种权限**，在“设置 > 智能体”里选，作用于所有文档：
   - **自动编辑：** 智能体直接修改文档，然后回复说明改了什么。回复上附带
     修改记录，人可以审阅、撤销。评论明确要求“先给方案”时，它也可以只提方案。
   - **手动批准：** 智能体不碰文档，只在回复里提出修改方案：要改哪段原文、
     改成什么。人点“应用”才真正修改文档。
3. **智能体总是回复，从不解决。** 改完、答完、需要追问，都以一条回复结束。
   解决和重新打开只能由人来做，CLI 和核心库会拒绝智能体的 resolve。
4. **回复把球交还给人。** 智能体回复后，由人决定：解决、继续回复、应用方案，
   或者撤销。界面上不另加“等你查看”之类的提示。

不变的部分：`working` 标记、批量运行、每小时次数和预算等限制、撤销（Undo）。

### 目标

- **行为可预期。** 动了一定回复，不替人判断“完成了没有”。
- **人决定放手的程度。** 可以让它直接改，也可以每处修改都先过目。
- **看得见过程。** 自动编辑的修改和人应用的方案，都以“光标移动 → 选中要删
  的文字 → 删除 → 逐字输入”的方式呈现；结束后保留高亮，方便事后审阅。
- **人优先，且什么都不丢。** 人可以在任何位置输入。冲突时人的文字保留，智能体
  的文字变成修改方案，不会悄悄消失。正常使用中不再出现“Needs your choice”。
- **互相看得见。** 人看得见智能体在哪里；智能体知道人正在写哪一段，并避开它。
- **修改记录准确。** 回复上的修改记录只包含智能体自己的修改。

### 非目标

- 复刻 Google Docs。只借鉴它的协作体验，不追求逐项对齐，也不做版本历史、
  在线分享等功能。
- 多人协作和网络同步。OpenDoc 始终是一个人加上若干智能体，因此也不引入
  CRDT（Yjs 等）。
- 在智能体输入途中改变它的写法。回放的是它已经写完的修改，看到它写偏了，
  只能等它回复后再 @ 它。
- 永久的作者着色。
- 让人的 Ctrl+Z 撤销智能体的修改。智能体的修改仍不进入人的撤销历史，撤销
  通过评论串上的“Undo”完成。
- 收紧智能体读取文件的权限。保持现状：`Read` 不限路径，只用 deny 规则挡住
  密钥类文件（`src/server/agents/adapters.js` 的 `DENIED_READS`）。

### 参考 Google Docs 的地方

| Google Docs 里的体验 | OpenDoc 的做法 | 取舍 |
| --- | --- | --- |
| 被 @ 的人才会去处理评论 | 评论默认交给智能体，只 @ 了别人的除外 | 有意的差异：少一步操作 |
| 评论由人决定是否解决 | 只有人能解决评论串 | 借鉴 |
| 建议模式：修改以建议出现，由作者接受 | 手动批准：方案放在回复里，选中评论串时在正文里预览，人点“应用” | 借鉴；方案存在 sidecar 里，不写进 markdown |
| 看得见对方的光标和名字，文字逐字出现 | 智能体光标，加上修改回放 | 借鉴；回放的是写完的修改，不是实时输入 |
| 两人在同一句里写，两边的字都在 | 段落内能合并就合并；合并不了时人的版本优先，智能体的版本变成修改方案 | 有意的差异 |
| 每个人的 Ctrl+Z 只撤销自己的修改 | 现在已经如此 | 借鉴 |
| 版本历史 | 用 git 和评论串里的修改记录 | 不做 |

### 使用体验

**自动编辑**

1. 人选中一段文字，评论“@claude 这段太长了，压缩一下”。
2. 几秒内，智能体的光标出现在这一段，旁边显示“正在看…”。
3. 文件写入后开始回放：要删的文字先以选区的样子高亮约 0.3 秒再消失，新文字
   逐字出现，带着格式（加粗就是加粗，不会先出现 `**`）。可以点“立即完成”。
4. 智能体回复“把三句合成了两句，删掉了重复的例子”。回复上有修改记录和
   “Undo”。
5. 改过的文字保留浅色高亮，直到人打开这个评论串或解决它。
6. 人觉得可以就解决；不满意就回复“@claude 保留第二个例子”，进入下一轮；
   或者点“Undo”。

**手动批准**

1. 前两步同上。
2. 智能体不修改文档，而是回复“建议把三句合成两句，删掉重复的例子”，回复下方
   列出修改方案：每处显示原文（删除线）和新文字。
3. 人选中这个评论串时，正文里以建议的样子预览这些修改：原文划掉，新文字插在
   后面。文档本身不变。
4. 人点“应用”（或逐处应用）：修改像自动编辑一样回放进文档并保存，评论串里
   记一条“fanzhangg 应用了 claude 的方案”，可以撤销。
5. 方案提出后原文被改动、找不到时，“应用”不可用，并提示“原文已改动”；人可以
   @ 它重新提。
6. 应用方案不会解决评论串，是否解决仍由人决定。

**同时编辑**（自动编辑时）

- 人在别的段落输入：互不影响。
- 人在正在回放的段落里输入：这一段剩下的回放立即补完，人的输入落在补完后的
  文字上。
- 人正在写的段落，智能体不会去改：它先改别处；一直改不了时，把这处修改作为
  修改方案写进回复。
- 人在某一段有未保存的输入，智能体恰好也改了这一段：先尝试段内合并；合并
  不了时保留人的版本，智能体的版本作为修改方案出现在评论串里。

手动批准时智能体不写文件，不会和人的输入冲突。文件被其他程序修改（git
checkout、别的编辑器）时，仍然一次性显示，不回放。

### 方案

分四个阶段，每个阶段都可以单独发布。阶段 1 是评论规则本身，最先做。

#### 阶段 1：评论规则与两种权限

改动在格式规范、核心库、CLI、调度器、技能说明、设置和评论边栏。

- **收件箱。** SPEC §5 保持“提及 P 或者没有提及任何人”，另外跳过应用方案的
  通知（和撤销通知一样）。`inbox` 的 `mentionsOnly` 选项和设置里的
  “所有评论 / 仅 @”开关删除。（曾改为只认 @，试用后撤回。）
- **只有人能解决。** SPEC §2.2 的“任何人都可以解决或重新打开”改为“只有
  `kind` 为 `human` 的参与者可以”。核心库的 `applyOp` 拒绝智能体发出的
  `resolve` 和 `reopen`；`opendoc resolve --as <智能体>` 报错退出；技能说明删掉
  “解决”这一步；调度器 `#recordEdits` 里“保持智能体已解决的评论串”那段删除；
  编辑器不再显示“Resolved by claude”。旧 sidecar 里由智能体解决的评论串保持
  原样，仍然有效。
- **权限设置。** 设置里的 `agent.mentionsOnly` 换成 `agent.editMode`：
  `"auto"`（自动编辑）或 `"approve"`（手动批准），默认 `"auto"`，与现在的
  行为一致。调度器把它带进提示；`"approve"` 时 Claude Code 的
  `--allowedTools` 不再包含 `Edit(./文档)`，智能体即使想改也会被 `dontAsk`
  直接拒绝。
- **修改方案。** 新增 `opendoc propose X.md <thread-id> --as claude`，从
  stdin 读 JSON：`{ "body": "说明", "changes": [{ "before": "原文", "after":
  "新文字" }] }`，都是 markdown 源码。每处 `before` 必须在当前文档中恰好出现
  一次（和 Claude Code 的 `Edit` 一样），否则报错，让智能体加长原文。通过后
  计算上下文，作为一条回复写入，消息带新字段 `proposal`。SPEC 新增 §2.6 描述
  它的形状：每处是 `before`、`after`，加上 `before` 两侧的上下文和位置提示。
- **应用方案。** 评论卡片显示方案的 diff 和“应用”按钮。应用时按 §2.5 撤销
  所用的定位规则（方向相反）在当前文本里找 `before` 及其上下文，找不到就
  禁用按钮。应用走普通编辑路径（阶段 2 之后走回放）并保存，然后以人的身份
  追加一条应用通知：消息带 `applies`（被应用的消息 id，类似 `undoes`）和这次
  修改的 `edits`，因此同样可以撤销。
- **正文预览。** 选中带方案的评论串时，编辑器用 decoration 预览：`before`
  加删除线，`after` 作为 widget 插在后面。只是装饰，不改文档。
- **修改记录只含智能体的修改。** 调度器不再比较“认领时”和“结束时”的整篇
  文档。服务器知道哪些磁盘变化来自编辑器的保存（`PUT /api/doc`）：运行期间，
  经由保存的变化属于人，其余磁盘变化属于这次运行，逐次累积成 `edits`。这对
  所有适配器都有效，不依赖 hook。
- **不做“等你查看”。** 曾实现为未读标记，试用后觉得是多余的提示，已删除。

#### 阶段 2：修改回放与在场感

改动集中在 `web/editor.js` 和 `web/main.js`，服务端不变。

- **运行一开始就出现。** 智能体状态里已经带着 `threadIds`。编辑器把智能体
  光标移到第一条评论锚定的段落，显示“正在看…”，直到第一次修改或运行结束。
- **只回放真正变了的字。** `diffBlocks` 会把相邻的几个改动段落合成一个 hunk。
  在 hunk 内先把新旧块按位置和相似度配对，配对的块内做字符级 diff（不只是
  现在 `changedRange` 的前后缀），只删除和输入变了的字；只改了格式时，先
  选中再加上或去掉格式。没有配对的块整块删除或插入，新块先插入空节点再填字。
- **用可映射的 step 回放。** 把当前文档到目标文档的修改拆成一串小的
  ProseMirror step，按动画帧逐个应用（每帧最多一个 transaction，带回放 meta，
  不进撤销历史）。尚未应用的 step 在人每次修改后用那次修改的 mapping 映射，
  和 prosemirror-collab 的 rebase 同理。这样人的任何输入，包括打字、粘贴、
  拖放、回车、工具栏、撤销和输入法，都不需要拦截。人的修改碰到正在回放的
  范围时，把这一块剩下的 step 一次应用。
- **输入法。** `view.composing` 为真时暂停回放，`compositionend` 后继续。
- **节奏。** 默认按字计速，约每秒 15–20 个，行尾停 0.2 秒、段落之间停 0.5 秒。
  一次修改的回放总时长有上限（初定 10 秒），超出时自动加速。速度和上限放进
  设置，提供“立即”。
- **保存和同步不能看到中间状态。**
  - `dirty` 改为按 transaction 判断：`docChanged` 且不带回放 meta 才算人的
    修改。现在 `onChange` 来自防抖后的 `markdownUpdated`，靠和 `baseline` 比较
    判断，看不到 meta，会把回放的中间状态当成人的输入。
  - 回放期间暂停保存，结束后再保存。
  - `doSync` 读取 `mine` 之前、`save` 处理 409 之前、`beforeunload` 判断之前，
    都先立即完成正在进行的回放；否则智能体写了一半的文字会被当成人的修改
    参与合并。
- **光标常驻。** 回放结束后，光标停在最后编辑的位置，随文档 mapping 移动；
  空闲一段时间（初定 30 秒）后变淡，下次运行开始时恢复。
- **事后审阅。** 回放结束后，改过的文字保留浅色高亮并带名字，直到人打开对应
  的评论串或解决它。取代现在 6 秒后消失的发光。
- **视图跟随。** 改动在视口里，或人此刻没有在输入时，视图跟随光标；否则只在
  编辑区边缘显示“claude 正在下方编辑 ↓”，点击跳过去。
- **评论高亮。** 回放期间只靠 mapping 跟随，结束后再 `paintHighlights`。
- **结果校验。** 回放结束后把编辑器内容和目标文档比对，不一致时直接用目标块
  替换，并记一条调试日志。
- **应用方案也走回放。**

#### 阶段 3：同段落冲突不再弹窗

改动在 `web/merge.js`、`web/main.js` 和调度器。

- **先尝试段落内合并。** 双方改了同一段时，在这一行 markdown 源码内部再做
  一次按字的三方合并：改的是不重叠的区间就两边都保留。合并结果重新解析一次，
  结构变了（例如拆坏了 `**`）就当作合并不了。
- **合并不了时，人的版本优先。** `merge3` 增加“冲突时取 ours”的模式。编辑器
  保留人的段落，正常保存，覆盖磁盘上智能体对这一段的修改。
- **被覆盖的修改变成方案。** 阶段 1 已经能区分人和智能体的磁盘变化。运行结束
  时，调度器发现某处智能体的修改已被人的保存覆盖，就把它转成修改方案，附在
  这次运行对相应评论串的回复上。方案的原文多半已经变了，“应用”不可用，但人
  能看到智能体原本想怎么改，需要时再 @ 它。
- **横幅只留给极端情况。** 例如文件被外部程序整个改写、无法按块对齐时，才
  回退到现在的“Needs your choice”。

#### 阶段 4：让智能体看见人

改动在 `web/main.js`、`src/server/server.js`、`adapters.js`，以及新的
`opendoc guard` 子命令。只有 Claude Code 适配器有 hook；自定义适配器只有
写进提示的那部分。手动批准时智能体不写文件，不需要这个阶段。

- **报告人的位置。** 编辑器把人正在编辑的块（最近 15 秒内在这一块里输入过；
  光标只是停着不算）发给本地服务器，节流到每秒最多一次。位置用磁盘上
  markdown 的行范围表示：人看到的是未保存的版本，而智能体的 `old_string`
  来自磁盘上的版本，必须在同一个坐标里比较。
- **写进提示。** 每次运行的提示里加一句：人正在编辑哪一段（引用它的开头），
  请先改别处。
- **用 hook 硬性避让。** 通过 `--settings` 给 `claude -p` 配一个匹配 `Edit` 的
  `PreToolUse` hook，调用 `opendoc guard`：在磁盘文件里定位 `old_string`，与人
  正在编辑的行范围重叠就拒绝，理由是“人正在这里输入，先改别处或稍后再试”。
  服务器地址和 token 通过环境变量传给 hook。
- **顺便告诉编辑器要改哪里。** 同一个 hook 把即将修改的位置报给服务器，编辑
  器先把智能体光标移过去、选中要改的文字。提前量只有工具执行前的一瞬间；想
  更早，可以加 `--include-partial-messages`，在模型生成 `new_string` 的那几秒
  里就从流式输出读出 `old_string`，作为后续优化。
- **一直改不了时转为方案。** 技能说明里约定：同一处被拒绝两次后不再重试，改用
  `opendoc propose`。

有了阶段 4，大多数冲突在发生之前就被避开；阶段 3 只处理检查和写入之间那一小
段时间里的竞争。

### 验收

每个阶段结束时跑一遍对应的场景。

1. 只 @ 了别人的评论：智能体不运行。其他评论：几秒内它的光标出现在评论
   所在的段落（阶段 2）。
2. 智能体处理完后，评论串保持打开，最新一条是它的回复。
   `opendoc resolve X.md <id> --as claude` 报错。
3. 手动批准：文件不变；评论卡片显示方案，选中时正文里有预览；点“应用”后文档
   修改并保存，评论串出现应用通知，点“Undo”能撤销。
4. 手动批准：方案提出后人改了那段原文，“应用”不可用并提示原文已改动。
5. 自动编辑时，人在第 5 段输入，同时 Claude 改第 2 段：回复上的修改记录只有
   第 2 段，点“Undo”不影响第 5 段。
6. 让 Claude 改写一个三段的小节：能看清每段具体改了哪些字，而不是整段重打；
   回放结束后高亮保留到人打开评论串（阶段 2）。
7. Claude 回放第 2 段时人也在第 2 段输入：回放立即补完，人的输入保留，不出现
   横幅（阶段 2）。
8. 回放进行到一半时关闭窗口：磁盘上是 Claude 的完整修改加上人的输入（阶段 2）。
9. 用中文输入法组字时 Claude 开始回放：组字不被打断（阶段 2）。
10. 人在第 2 段有未保存的输入，Claude 同时改写第 2 段：不出现横幅，保留人的
    版本，评论串里出现 Claude 的方案（阶段 3）。
11. 人一直在第 2 段输入，同时 @claude 改写第 2 段和第 4 段：第 4 段被改写；第
    2 段不变，回复里有对第 2 段的方案（阶段 4）。

### 风险

- **给自己的备注也会唤醒智能体。** 不需要 @ 之后，人写给自己的备注也会触发
  一次运行。可以 @ 自己来避免。
- **自动保存让智能体的 `Edit` 失败。** Claude Code 的 `Edit` 会检查文件在上次
  `Read` 之后有没有被改过。人一边打字一边自动保存（约 800 毫秒一次）时，智能体
  可能被反复要求重新读取，消耗轮数。阶段 1 就要实测；严重的话，在技能说明里
  写明“`Edit` 因文件变化失败时，重新读取后只重试一次”，并考虑提高默认轮数。
- **`before` 不唯一或已过时。** `propose` 当场报错，让智能体加长原文；人迟迟
  不应用导致原文变了，“应用”会禁用，不会改错地方。
- **transaction 太多。** 切片按动画帧合并，回放期间跳过评论高亮重绘。
- **回放和 markdown 往返不一致。** 有结果校验兜底，不一致时用目标块替换并记
  日志，便于补上遗漏的节点类型。
- **长改写。** 总时长上限加自动加速；仍然难读时，在技能说明里鼓励小步修改。
- **hook 的行为未经验证。** 阶段 4 开始前确认四件事：`--settings` 能否给
  `claude -p` 传入 hook；`dontAsk` 下 `PreToolUse` 的拒绝是否生效；拒绝理由是否
  回到模型；隔离模式（`--bare`）是否仍加载 `--settings` 里的 hook。任何一项不
  成立，就退回“只写进提示”，由阶段 3 兜底。
- **位置信息会过时。** hook 查询和文件写入之间，人可能刚好开始在那一段输入。
  这段时间很短，由阶段 2 的“立即补完”和阶段 3 的合并兜底。
