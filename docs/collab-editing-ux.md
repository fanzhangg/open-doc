## 协作编辑体验改进

### 概述

MVP 的目标：人和智能体共同编辑一篇文档的体验，复刻 Google Docs 上人和人共同
编辑的体验。是否做到，按下文的[对照表](#对照google-docs-的体验)逐项验收。

现在智能体的修改是“一次性出现”的：磁盘上的文件一变，编辑器就把变化的段落
整块替换掉，并让新文字发光 6 秒。人看到的是结果，而不是过程；如果人恰好在
同一段落里还有未保存的输入，就会弹出“Needs your choice”，要求在两个完整版本
之间二选一。智能体也看不到人在哪里，只能在冲突发生之后再收拾。

本方案让智能体像一个坐在旁边的合著者那样编辑：它一直在场，开始工作时光标先
移到要看的地方，删掉的文字先被选中再消失，新文字一个字一个字地打出来；它也
知道人正在写哪一段，会主动避开。人可以随时在任何地方继续输入，人的输入始终
优先，也绝不会因为智能体的修改而被迫做选择。

方案不改变现有的数据模型：磁盘上的 markdown 仍是唯一的真实来源，sidecar、
锚定、保存时保留未改动块的原始字节都保持不变。改动集中在编辑器“如何呈现”
磁盘上的变化、冲突时“谁优先”，以及让双方互相看得见。

相关文档：[产品设计](product-design.md)、[桌面应用设计](desktop-app.md)

### 问题

- **修改像“神迹”。** `applyMarkdown`（`web/editor.js`）用 `replaceWith` 一次替换
  所有变化的块。改动跨几个段落时，人很难看清改了什么、从哪里改起。
- **同段落冲突会打断人。** `merge3`（`web/merge.js`）按行（约等于段落）合并，
  双方改了同一段就返回冲突，`showConflict` 弹出横幅。选“Keep mine”会用人的版本
  覆盖智能体的全部修改，选“Use their version”会丢掉人未保存的输入。
- **看不到智能体在哪里。** 头像能显示它在工作，但看不出它在看哪里、接下来要改
  哪里；运行开始后的十几秒到几十秒里，页面上什么都不动。
- **智能体看不到人在哪里。** 它不知道人正在写哪一段，会径直改那一段。Google Docs
  里很少出冲突，主要不是靠合并算法，而是双方都看得见对方、自然会避开。
- **署名靠猜。** `editorName` 根据“当前有没有智能体在运行”推测是谁改了文件。
  只有一个智能体时够用，有多个时就不对了。

### 目标

- **看得见过程。** 智能体的每次修改都以“移动光标 → 选中要删的文字 → 删除 →
  逐字输入”的方式呈现，速度足够慢，能跟着读。
- **一直在场。** 智能体的光标不只在输入时出现：开始工作时就出现在它要看的地方，
  工作结束后停在最后编辑的位置。
- **互相看得见。** 人看得见智能体在哪里；智能体也知道人正在写哪一段，并避开它。
- **人优先，且什么都不丢。** 人可以在任何位置输入，包括智能体正在输入的那一段。
  人的文字永远保留；智能体的文字要么也保留，要么作为建议放进评论串，不会悄悄
  消失。
- **不再为冲突弹窗。** 正常使用中不出现“Needs your choice”。
- **为多个智能体做好准备。** 每次修改都知道是哪个智能体做的，每个智能体有自己的
  名字、颜色和光标。

### 非目标

- 多人协作。OpenDoc 始终是一个人加上若干智能体，不做网络同步，因此也不引入
  CRDT（Yjs 等）。磁盘上的 markdown 加按块合并对这个场景已经足够。
- 在智能体输入途中改变它的写法。智能体是先写完一次修改、再把它呈现出来的；
  看到它写偏了，只能等它写完后留评论，不能半路叫停让它改写。
- 永久的作者着色（每段文字一直显示是谁写的）。
- 让人的 Ctrl+Z 撤销智能体的修改。智能体的修改仍不进入人的撤销历史
  （`addToHistory: false`），撤销仍通过评论串上的“Undo”完成。这正好和 Google Docs
  一致：每个人的 Ctrl+Z 只撤销自己的修改。
- 收紧智能体权限。保持现状：`Edit` 只限当前文档；`Read` 不限路径，只用 deny
  规则挡住密钥类文件（`.env*`、`*.pem`、`*.key`、`~/.ssh`、`~/.aws`，见
  `src/server/agents/adapters.js` 的 `DENIED_READS`）。

两处有意接受的差异：

- **同一句里的重叠修改不会两边都保留。** Google Docs 会把双方的字都合并进去；
  本方案在段落内合并不了时，以人的版本为准，智能体的版本作为建议保留。有了
  阶段 4 的事前避让，这种情况应该很少出现。
- **不能半路叫停。** 见非目标。真人协作者其实也是先想好再打字，大多数时候看不出
  区别。

### 使用体验

1. 人在一段文字上留评论，`@claude` 开始处理。智能体的光标立即出现在评论所在的
   段落，旁边显示“正在看…”。
2. Claude 决定修改时，光标移到要改的位置，选中要改的文字。文件写入后开始回放。
3. 要删的文字先以选区的样子高亮一下（约 0.3 秒），然后消失。
4. 新文字逐字出现，带着格式（加粗就是加粗，不会先出现 `**`）。行尾、段落之间
   略作停顿。新段落先出现一个空的块，再往里填字。
5. 如果改动的位置在视口里，或者人此刻没有在输入，视图跟随光标滚动；否则不抢
   视图，只在编辑区边缘显示“claude 正在下方编辑 ↓”，点击可以跳过去。
6. 回放过程中可以点“立即完成”，剩下的部分一次显示。
7. 人在别的段落输入：互不影响。
8. 人在智能体正在输入的那一段里动手：这一段的回放立即补完，人的这次输入落在
   补完后的文字上。人的文字不丢，智能体的文字也不丢。
9. 人正在写的段落，智能体不会去改：它会先改别处，或者稍后再试；一直改不了时，
   把想改的内容作为建议写进评论串。
10. 回放全部结束后，评论卡片才显示“Resolved by claude”。智能体的光标留在最后
    编辑的位置，空闲一段时间后变淡。

文件被其他程序修改（git checkout、别的编辑器）时，仍然一次性显示，不回放。
回放只用于智能体的修改。

### 方案

分四个阶段，每个阶段都可以单独发布。

#### 阶段 1：逐字回放

改动集中在 `web/editor.js` 和 `web/main.js`，服务端不变。

- **回放代替替换。** `applyMarkdown` 照旧用 `diffBlocks` 算出变化的块，但不再
  直接 `replaceWith`，而是交给一个回放器。单块改单块时，用现有 `changedRange`
  的前后缀算法找出块内真正变化的字符；多块变化时，先删旧块，再逐块插入新块。
- **在 ProseMirror 层面回放，而不是 markdown 源码。** 插入的是目标文档里已经
  带 mark 的文本节点，按字切片插入；新块先插入空节点再填字。这样永远不会出现
  半截的 markdown 语法。
- **智能体光标。** 一个 widget decoration，复用现有 `flag(by)` 的样式，再加一条
  竖线。随每个切片的 transaction 一起移动。
- **光标常驻。** 回放结束后，光标留在最后编辑的位置，随文档 mapping 移动；
  空闲一段时间（初定 30 秒）后变淡，下次运行开始时恢复。
- **节奏。** 默认按“字”计速（一个汉字或一个拉丁字母都算一个），约每秒 15–20 个，
  行尾停 0.2 秒、段落之间停 0.5 秒。一次修改的回放总时长有上限（初定 10 秒），
  超出时自动加速，避免整篇改写要看好几分钟。速度和上限放进设置，提供“立即”。
- **回放期间暂停保存。** 磁盘上已经是 Claude 写完的版本，回放产生的中间状态不能
  写回去。回放器的 transaction 带一个 meta，`onChange` 遇到它不置 `dirty`；人在
  回放期间的输入照常置 `dirty`，但保存要等回放结束后再进行。关闭窗口时
  （`beforeunload` / `flushSave`）先立即完成回放，再保存。
- **人优先。** 在 `handleTextInput` / `handleKeyDown` 里判断：人的输入落在正在
  回放的块里时，先把这个块剩下的部分一次补完，再让人的输入生效。
- **输入法。** `view.composing` 为真时（中文、日文输入法正在组字）暂停回放，
  `compositionend` 后继续，否则回放的 transaction 会打断组字。
- **队列。** 一次运行可能多次写入文件。新的磁盘变化到达时，若上一次回放还没
  结束，先立即完成它，再以当前文档为起点开始新的回放。
- **评论高亮。** 回放期间不重新定位评论高亮（中间状态里引文可能暂时不存在），
  只靠 mapping 跟随；回放结束后再 `paintHighlights`。
- **结果校验。** 回放结束后，把编辑器内容和目标文档比对；不一致时（例如某种
  节点的回放没覆盖到）直接用目标块替换，保证最终结果和磁盘一致。
- **延后显示“已解决”。** `doSync` 里 sidecar 和文档一起到达，但对正在回放的
  评论串，“Resolved by claude”在回放结束后才显示。

#### 阶段 2：同段落冲突不再弹窗

改动在 `web/merge.js` 和 `web/main.js`。

- **先尝试段落内合并。** 双方改了同一段时，在这一段内部再做一次按字的三方合并：
  改的是不重叠的字符区间就两边都保留。
- **合并不了时，人的版本优先。** `merge3` 增加一个“冲突时取 ours”的模式，并返回
  被放弃的那些智能体段落。编辑器保留人的段落，正常保存（会覆盖磁盘上智能体
  对这几段的修改）。
- **智能体的版本变成建议。** 被放弃的段落以一条消息加到触发这次运行的评论串里：
  “claude 想把这一段改成：……”，附“应用”按钮。点“应用”就像一次普通编辑那样
  替换这一段（走阶段 1 的回放）。
- **横幅只留给极端情况。** 例如文件被外部程序整个改写、无法按块对齐时，才回退到
  现在的“Needs your choice”。

阶段 2 完成后，评论串里记录的 `edits` 可能和最终文本不一致；“Undo”已经会在
文本对不上时报“Cannot undo”，行为可以接受，不另做处理。

#### 阶段 3：智能体的在场感与署名

改动在 `src/server/agents/adapters.js`、`dispatcher.js` 和 `web/agent.js`。

- **运行一开始就出现。** 调度器认领评论串、启动运行时，通过事件流告诉编辑器
  “claude 在处理这几条评论”。编辑器把智能体光标移到第一条评论锚定的段落，
  旁边显示“正在看…”，直到第一次修改或运行结束。这段等待（启动加思考，常常
  十几秒以上）无法消除，但人能看到它在做事、在哪里做。
- **提前知道修改的位置。** 把 Claude Code 的输出从 `--output-format json` 改成
  `stream-json`。调度器在看到 `Edit` 的 `tool_use` 时（文件还没写入），就从
  `old_string` 定位到文档里的位置，通过事件流告诉编辑器。编辑器先把智能体光标
  移过去、选中要改的文字；文件写入后再接着回放。
- **明确署名。** 服务端在推送文档变化时，附上是哪个智能体的哪次运行写的，
  取代 `editorName` 的推测。没有署名的变化一律视为“Edited on disk”，一次性显示。
- **为多个智能体预留。** 光标、颜色、回放队列都按智能体区分。不同智能体在不同
  的块里可以同时回放；在同一块里则排队。调度器目前一次只跑一个运行，是否并发
  运行多个智能体不在本方案范围内，但编辑器这一侧不应假定只有一个。

#### 阶段 4：让智能体看见人

改动在 `web/main.js`、`src/server/server.js`、`adapters.js`，以及一个新的
`opendoc` 子命令。

- **报告人的位置。** 编辑器把人光标所在的块，以及最近一次输入的时间，发给本地
  服务器（节流，例如每秒最多一次）。只有最近一段时间内（初定 15 秒）在这一块里
  输入过，才算“正在编辑”；光标只是停在那里不算，否则人离开电脑后这一段就永远
  改不了。
- **写进提示。** 每次运行的提示里加一句：人正在编辑哪一段（引用它的开头），
  请先改别处。
- **用 hook 硬性避让。** 通过 `--settings` 给 `claude -p` 配一个 `PreToolUse`
  hook，匹配 `Edit`。hook 调用新的 `opendoc guard` 子命令：读入工具参数，向本地
  服务器查询人此刻正在编辑的块，判断 `old_string` 是否落在其中。落在其中就拒绝，
  理由是“人正在这里输入，先改别处或稍后再试”；否则放行。服务器地址和 token 通过
  环境变量传给 hook。
- **一直改不了时转为建议。** 技能说明里约定：同一处被拒绝两次后，不再重试，
  而是把想改的内容作为建议写进评论串，与阶段 2 的建议消息格式一致。

有了阶段 4，大多数冲突在发生之前就被避开；阶段 2 只处理检查和写入之间那一小段
时间里的竞争。

### 验收

用下面几个场景手动验证，每个阶段结束时都跑一遍对应的场景。对照表的每一行都
指向其中一个场景。

1. 让 Claude 改写一个三段的小节：能看清它从哪里开始、选中并删了什么、写了什么。
2. Claude 在第 2 段输入时，人在第 5 段输入：双方都不被打断，最后两处修改都在
   磁盘上。
3. Claude 在第 2 段输入时，人也在第 2 段输入：Claude 的这一段立即补完，人的输入
   保留，不出现横幅。
4. 人在第 2 段有未保存的输入，Claude 同时改写了第 2 段（阶段 2）：不出现横幅，
   编辑器保留人的版本，评论串里出现 Claude 的建议。
5. 回放进行到一半时关闭窗口：磁盘上是 Claude 的完整修改加上人的输入。
6. 用中文输入法组字时 Claude 开始回放：组字不被打断。
7. Claude 改完后一分钟内不再操作：它的光标仍停在最后编辑的位置，逐渐变淡。
8. 留下评论后（阶段 3）：几秒内 Claude 的光标出现在评论所在的段落并显示
   “正在看…”；它动手前，光标先移到要改的地方。
9. 人一直在第 2 段输入，同时让 Claude 改写第 2 段和第 4 段（阶段 4）：第 4 段被
   改写；第 2 段不被改动，评论串里出现 Claude 对第 2 段的建议。

### 风险

- **transaction 太多。** 每个切片一个 transaction，加上 decoration 更新。切片按
  动画帧合并（每帧最多一个 transaction），并在回放期间跳过评论高亮重绘。
- **回放和 markdown 往返不一致。** 节点级回放后序列化的结果，可能和
  `normalize(theirs)` 不完全相同。有结果校验兜底；不一致时用目标块替换，并记一条
  调试日志，便于补上遗漏的节点类型。
- **长改写。** Claude 可能一次改写整篇文档。总时长上限加自动加速可以兜住；如果
  仍然难以阅读，再考虑在技能说明里鼓励小步修改。
- **`stream-json` 的格式。** 阶段 3 依赖 Claude Code 流式输出中 `tool_use` 事件的
  形状，需要在开始前确认，并锁定兼容的版本范围。
- **hook 的行为未经验证。** 阶段 4 开始前要确认三件事：`--settings` 能否给
  `claude -p` 传入 hook；`dontAsk` 模式下 `PreToolUse` 的拒绝是否生效；拒绝理由
  是否会回到模型那里，让它改去别处。任何一项不成立，就退回“只写进提示”，由
  阶段 2 兜底。
- **位置信息会过时。** hook 查询和文件写入之间，人可能刚好移到那一段开始输入。
  这段时间很短，由阶段 1 的“立即补完”和阶段 2 的合并兜底。
- **人优先会让智能体看到的和它写的不一样。** 阶段 2 覆盖了智能体的修改后，
  Claude 下一次运行读到的是人的版本。这是期望的行为，但它可能会重复同样的修改；
  评论串里的建议消息可以让它知道上一次被放弃了。

### 待解决问题

- 默认速度：散文和列表、代码块是否需要不同的速度？
- 视图跟随的规则：人“没有在输入”的判定用多长的空闲时间？
- “正在编辑”的判定：15 秒是否合适？选中一段文字但没有输入，算不算？
- 智能体光标空闲多久后变淡？是否在头像上提供“跳到 claude 所在位置”？
- 阶段 2 和阶段 4 的建议消息放在原评论串里，还是在相关段落上新建一个评论串？
- 多个智能体时，是否需要让人看到每个智能体“排队中”的修改？
- 智能体的权限（`Read` 不限路径）是否在出现多个、来源不同的智能体时收紧？
