## 产品设计

### 概述

OpenDoc 让人和 AI 智能体通过锚定在文本上的评论串，共同撰写一个普通的
markdown 文件。文档始终是普通 markdown；评论保存在旁边的 sidecar 文件中
（`plan.md` → `plan.md.opendoc.json`），无论哪一方编辑文档，评论都会附着在
对应的文本上。人在一个类似 Docs 的桌面应用中工作，它像普通编辑器一样打开
markdown 文件；智能体则通过 CLI 和它常用的文件工具工作。双方看到的是同一组
评论串。

### 问题

- 智能体很擅长编辑 markdown 文件，但引导它们的方式是一个与文档分离的聊天
  窗口。像“这一段太长了”这样的反馈，只能描述它针对哪里，而不能直接指向那里。
- 托管的文档工具有行内评论，但内容存放在它们的服务里，而不是仓库中的
  markdown 文件里，智能体也难以读取或回复这些评论。
- 写入 markdown 的评论标记（HTML 注释、自定义语法）会污染文件、破坏其他地方
  的渲染，并产生杂乱的 diff。

### 目标

- **在文本上评论，而不是在聊天中。** 每个请求或问题都是一个评论串，附着在
  它所针对的段落上，或附着在整篇文档上。
- **普通文件。** 文档始终是普通 markdown，在任何地方都能渲染，在 git 中 diff
  干净。所有 opendoc 数据都在一个格式公开的 JSON sidecar 中。
- **锚点在编辑后依然有效。** 当周围文本被编辑、移动或改写时，评论串仍保持
  附着；文本被删除时，评论串也绝不会被悄悄丢失。
- **智能体作为合著者。** 智能体像一个普通的协作者：被 @ 时处理评论串，按
  人选择的权限直接修改文档或提出修改方案，并在评论串中回复，人无需切换工具。
  评论串是否完成由人决定，只有人能解决评论串。
- **安全的并发编辑。** 智能体在文档其他位置编辑时，人可以继续输入；双方都
  不会丢失对方的修改。
- **真正的桌面编辑器。** 可以从应用中或直接从文件系统打开文档，在任意文件夹
  中新建文档，一次设置字体等偏好即可作用于所有文档和每次启动，并在“设置”中
  配置智能体，而不是通过命令行参数。

### 非目标（v1）

- 通过网络的实时多人协作。编辑器是单台机器上的桌面应用，供一个人及其
  智能体使用。
- 超出 markdown 的富文本格式，或专有文档格式。
- 托管、账户或分享。

### 用户

首批目标用户是作者本人：在自己的项目（例如 vibe coding 项目）里需要写
markdown 文件时，直接在编辑器里写。要优化的场景是编辑 markdown 文件本身，
不针对特定的内容类型。

- **作者：** 撰写计划、规范或设计文档的人，希望智能体帮助起草、修改并回答
  有关问题。
- **智能体：** Claude Code（或其他智能体 CLI），作为一个有名字的参与者，
  例如 `@claude`。
- **审阅者：** 评论串中被提及的另一个人，例如 `@alex`。智能体和审阅者遵守
  同样的规则：没有 @ 它的评论不会唤醒它。

### 核心概念

- **文档（Doc）：** 任意 markdown 文件 `X.md`。
- **Sidecar：** `X.md.opendoc.json`，保存参与者和评论串。在第一条评论时创建；
  用 `opendoc mv` 重命名文档时会一并移动。
- **评论串（Thread）：** 一个锚点加上若干消息，按时间从旧到新排列。状态为
  打开或已解决；只有人可以解决或重新打开，新消息会重新打开它。
- **锚点（Anchor）：** 被引用的文本，加上两侧各最多 32 个字符的上下文和一个
  位置提示，基于文档的渲染文本（去掉 markdown 语法）计算。没有锚点的评论串
  针对整篇文档。
- **提及与收件箱：** 当评论串处于打开状态、最新消息来自人，并且该消息提及了
  某个参与者时，该评论串就在这个参与者的收件箱中。没有提及任何人的评论是人
  的备注，不进任何人的收件箱。收件箱仅根据 sidecar 计算。
- **编辑权限：** 在“设置 > 智能体”里选择。**自动编辑**：智能体直接修改文档，
  再回复说明改了什么。**手动批准**：智能体不修改文档，只在回复里提出修改
  方案，人点“应用”后才修改。
- **处理中（Working）：** 智能体回复评论串期间，评论串显示“claude is working
  on it”；该标记 5 分钟后过期。
- **修改记录（Edits）：** 智能体的回复可以记录它对文档的修改，方便人审阅和
  撤销。只记录智能体自己的修改，不包含人在同一时间的输入。
- **修改方案（Proposal）：** 智能体的回复可以附带尚未应用的修改：要改的原文
  和新文字。人应用后，它就和普通修改一样可以撤销。

### 使用体验

**人，在桌面应用中：**

1. 从应用中（打开、打开最近的文件）或从文件系统（双击 `.md`、“打开方式”、
   拖到应用上）打开文档，或在自选的文件夹中新建文档。每个文档在独立的窗口
   中打开，人以可视化方式编辑。
2. 选中文本，点击页面边缘的评论按钮（或按 Ctrl+Alt+M）。评论显示在对应文本
   旁边的页边；输入 `@` 会自动补全参与者。
3. 评论里 @ 了智能体，它才会接手。接手时它的头像显示正在处理，光标出现在
   评论所在的段落。自动编辑时，它的修改在页面中逐字回放并以其名字高亮，与人
   在其他位置的输入合并。
4. 智能体在评论串中回复：说明改了什么、提出修改方案、回答或追问。评论串保持
   打开，显示为“等你查看”；由人决定解决、继续 @ 它、应用方案或撤销。
5. 磁盘上文件的变化会实时显示。人和智能体改到同一段落时，先尝试段内合并；
   合并不了时保留人的版本，智能体的版本作为修改方案出现在评论串里。
6. 保存时保留每个未改动块的原始字节，因此 `git diff` 只显示真正的修改。
7. 设置（名字、主题、字体、宽度、编辑器开关、智能体选项）是全局的：修改会
   作用于所有打开的窗口，并保留到下次启动。

`opendoc serve plan.md` 仍会在浏览器标签页中打开同一个编辑器，使用相同的
已保存设置。

**智能体，通过 CLI：**

1. `opendoc wait X.md --as claude` 会阻塞，直到有 @ 它的评论串在等待，然后
   将其标记为正在回复并输出。
2. 智能体用它常用的文件工具读取 `X.md`；自动编辑时直接编辑它，手动批准时用
   `opendoc propose` 提出修改方案。
3. `opendoc reply` 回复评论串。智能体不能解决评论串。
4. 再次等待。`opendoc` 技能把这个循环教给 Claude Code。

**由应用启动的智能体**（设置 > 智能体，或
`opendoc serve X.md --agent claude`）：应用自己等待评论，并为每一批 @ 了它的
评论串启动一次无界面的智能体运行，人无需一直保持一个终端循环。

### 组件

| 组件 | 作用 |
| --- | --- |
| 格式规范 + JSON Schema | 定义 sidecar、锚点、重新锚定、提及、收件箱和写入协议，使其他工具可以互操作。 |
| 核心库 | 将 markdown 渲染为文本，根据选区或引用创建锚点，并在文档变化后重新锚定评论串。在 Node 和浏览器中输出一致。 |
| CLI | `comment`、`comments`、`inbox`、`wait`、`reply`、`propose`、`resolve`（仅限人）、`mv`；每个命令都支持 `--json` 和稳定的退出码。 |
| 编辑器页面 | 类似 Docs 的编辑器：实时文件同步、与未保存的输入合并、页边评论。以带 token 的方式在 `127.0.0.1` 上提供给桌面应用窗口或浏览器标签页。 |
| 桌面应用 | Electron 外壳：每个文档一个窗口和一个本地服务器，打开/最近的文件，在任意文件夹中新建和重命名文档，操作系统文件关联，菜单。 |
| 设置存储 | 一个用户级的 `settings.json`，由所有窗口和 `opendoc serve` 共享。 |
| 智能体调度器 | 在“设置”中开启或使用 `serve --agent` 时，为等待中的评论串运行智能体。 |
| 智能体技能 | 教智能体掌握协同写作循环的说明。 |

### 关键设计决策

- **使用 sidecar 而不是行内标记。** 让文档保持可移植、diff 保持干净，代价是
  需要锚定机制来让评论保持附着。
- **在渲染文本上锚定。** 加粗等格式变化不会移动或破坏锚点，智能体也可以直接
  引用它看到的内容。
- **分层重新锚定。** 先精确匹配，再用引文周围未改变的上下文定位，再做模糊
  匹配；都不行时将评论串标记为 `detached`，并保留其最后的引文。重新锚定是
  确定性的，因此并发的工具会得到一致的结果。
- **智能体是普通协作者。** 智能体和真人审阅者遵守同样的规则：被 @ 才处理，
  处理完一定回复，评论串由人解决。这样它什么时候会动、动了之后在哪里看结果，
  都是可预期的；代价是人每次都要 @ 它。
- **收件箱由 sidecar 推导。** 不需要游标或服务器状态；任何工具都能判断谁
  该回复。
- **加锁、重新读取、应用、重命名。** 写入方获取一个短暂的排他锁，并以客户端
  生成的 id 应用操作，因此并发写入方不会丢失修改，重试最多只生效一次。
- **Electron，复用本地服务器。** 服务器、文件监视器和智能体调度器都是 Node
  代码，应用可以原样运行它们，每个窗口加载与 `opendoc serve` 相同的编辑器
  页面。代价是下载体积更大。
- **设置保存在用户文件中，而不是浏览器里。** 浏览器存储以服务器的随机端口
  为键，因此每次运行都会丢失。现在设置保存在用户配置文件夹中的一个文件里，
  由本地服务器提供，因此重启后依然保留，并作用于所有窗口。
- **智能体运行受到限制。** 由服务器启动的运行只能读取文件、编辑当前文档
  （手动批准时不能编辑）和调用 `opendoc`；运行按批次逐个进行，并限制轮数、运行时间、每小时运行次数
  以及可选的预算。失败的运行会显示提示，在人回复或点击“重试”之前不会重试。
